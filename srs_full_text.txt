1. Introduction
1.1 Purpose
This document defines the functional and non-functional requirements for the Appointment Booking
Application. It serves as the authoritative reference for developers, designers, testers, and project
managers throughout the development lifecycle. The specification outlines the expected system
behavior, constraints, and quality attributes that must be satisfied for the application to be considered
complete and ready for deployment. All stakeholders should refer to this document as the single source
of truth for requirements scope and acceptance criteria.
1.2 Context
Manual appointment scheduling through phone calls, spreadsheets, or paper logs is error-prone,
time-consuming, and unavailable outside business hours. Common problems include double-bookings,
no-shows, inconsistent availability information, and excessive administrative overhead. These issues
lead to wasted resources, frustrated clients, and revenue loss for service providers who rely on efficient
scheduling to maximize their utilization rates.
This application digitizes the entire appointment lifecycle — from defining available time slots through
booking, confirmation, modification, and cancellation — providing a self-service experience for clients
and a centralized management interface for administrators. By replacing manual processes with an
automated, rule-based system, the application eliminates the most common sources of scheduling error
while improving accessibility and transparency for all users.
1.3 Objectives
• Eliminate double-bookings through real-time slot locking and database-level transaction
isolation.
• Provide 24/7 availability so clients can book at any time without human intervention.
• Reduce administrative burden by automating schedule creation, conflict detection, and booking
confirmations.
• Ensure data integrity with secure authentication, encrypted storage, and audit-ready logging.
• Deliver a responsive experience that works on desktops, tablets, and mobile devices.
1.4 Scope
In Scope: User registration and authentication; admin-defined time slot management; real-time
availability browsing; appointment booking with confirmation; booking cancellation; admin dashboard
for schedule oversight; email notification on booking events.
Out of Scope: Online payment processing; video conferencing integration; multi-provider marketplace;
SMS notifications; calendar sync (Google/Outlook); analytics and reporting dashboards; native mobile
applications.

 3. Functional Requirements
3.1 User Registration (FR-01)
The system shall allow new users to create an account using a valid email address and a password
meeting minimum complexity requirements (8+ characters, at least one uppercase letter and one
number). A confirmation email must be sent before the account is activated. The registration process
should validate email uniqueness in real-time and provide clear feedback on password strength. Upon
successful registration, the user receives a verification email containing an activation link that expires
after 24 hours. Unverified accounts are automatically purged after 7 days to maintain database hygiene.
3.2 User Authentication (FR-02)
The system shall authenticate users via email and password. Upon successful login, a signed JWT shall
be issued with a configurable expiry period (default: 1 hour for access tokens, 7 days for refresh tokens).
Failed login attempts shall be rate-limited to a maximum of 5 attempts per 15-minute window per IP
address. After exceeding this threshold, the account is temporarily locked and the user receives a
notification email. The authentication middleware validates the JWT signature and expiry on every
protected API request, ensuring that expired or tampered tokens are rejected immediately.
3.3 Slot Creation by Admin (FR-03)
Administrators shall be able to define available time slots by specifying a date, start time, end time, and
slot capacity. The system must validate slots to prevent overlaps with existing slots for the same date.
When a new slot conflicts with an existing one, the API returns a 409 Conflict response with details of
the overlapping slot. Administrators may also create recurring slots (e.g., every Monday from 9:00 to
12:00) to reduce repetitive data entry. Each slot records its creator, creation timestamp, and current
booking count for audit purposes.
3.4 Browse Available Slots (FR-04)
Clients shall be able to view all available (unfilled) time slots sorted by date and time. The interface
must indicate remaining capacity for each slot and display fully booked slots as unavailable. The slot
listing supports date-range filtering and pagination to handle large datasets efficiently. Slot availability
data is served from a read-optimized query with indexed columns on date and status, ensuring
sub-200ms response times even with thousands of slot records. The display distinguishes between
partially booked slots (showing remaining capacity) and fully booked slots (grayed out or hidden based
on user preference).
3.5 Book an Appointment (FR-05)
A logged-in client shall be able to book an available slot. The system must verify slot availability at the
moment of booking using a database-level lock (SELECT ... FOR UPDATE within a transaction) to
prevent race conditions when multiple clients attempt to book the same slot simultaneously. A
confirmation must be displayed to the client and an email sent to the registered address. The booking
record includes the client ID, slot ID, booking timestamp, and an initial status of "confirmed." If the slot
becomes fully booked during the transaction, the system returns a clear error message and the client is
prompted to select another slot.
3.6 Cancel an Appointment (FR-06)
Clients may cancel their own bookings at any time. Upon cancellation, the slot capacity must be
incremented immediately, making it available for other clients. A cancellation confirmation email shall
be sent to the client. The booking status transitions from "confirmed" to "cancelled" and the cancellation
timestamp is recorded. Administrators may also cancel bookings on behalf of clients, in which case both
the client and the admin receive confirmation emails. Cancelled bookings remain in the system for
historical reference and are not physically deleted.
3.7 View Booking History (FR-07)
Clients shall access a list of all their past and upcoming bookings, including status (confirmed,
cancelled), date, time, and slot details. The booking history view supports filtering by status and date
range, and presents records in reverse chronological order (most recent first). Administrators shall see all
bookings across all clients, with the ability to filter by client name, date range, and status. The history
view implements server-side pagination to maintain performance as the dataset grows over time.
3.8 Admin Schedule Overview (FR-08)
The admin dashboard shall display a consolidated view of all slots and their booking status (empty,
partial, full) for any selected date range. The overview provides at-a-glance visibility into schedule
utilization, helping administrators identify underutilized time periods and plan capacity adjustments. The
dashboard includes summary statistics such as total slots, total bookings, and average fill rate for the
selected period. The schedule view updates in near-real-time, reflecting new bookings within 30 seconds
of creation.
3.9 Slot Deletion by Admin (FR-09)
Administrators may delete a slot only if no bookings are associated with it. If bookings exist, the system
must reject deletion and prompt the admin to cancel individual bookings first. This safeguard prevents
accidental data loss and ensures that clients with confirmed bookings are not left without notification.
The deletion is a soft delete — the slot is marked as inactive rather than removed from the database,
preserving referential integrity for historical reporting and audit trails.
3.10 Email Notifications (FR-10)
The system shall automatically send email notifications for: successful registration, booking
confirmation, booking cancellation, and optionally upcoming appointment reminders as configured by
the admin. Email delivery is handled asynchronously via a job queue to prevent API response delays.
Failed email deliveries are retried up to 3 times with exponential backoff. All email events (sent, failed,
bounced) are logged for troubleshooting. In-app notifications serve as a fallback when email delivery
fails, ensuring the client always receives timely information about their booking status.

6.2 High-Level Data Flow — Booking Process
The booking process data flow involves four components: the Client Browser, the API Server
(Express.js), the MySQL Database, and the Email Service (SMTP via Nodemailer). The client sends an
HTTP request to the API server, which executes a SQL query against the database. The result set is
returned as a JSON response to the client. Concurrently, certain operations (booking confirmation,
cancellation) trigger the email service to send notifications. All database operations are wrapped in
transactions to ensure atomicity, and the API server enforces authentication and authorization before
processing any protected endpoint.
